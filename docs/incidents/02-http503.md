# Exercise 2: application route returns HTTP 503

**2026-11-15 · local lab · no real users affected**

A temporary, syntactically valid NGINX configuration made `/` return HTTP 503 on
both replicas. The existing SLO rules detected the failed requests and sent a
critical notification to the internal webhook mock. The runner restored both
configs as soon as delivery was confirmed. No alert thresholds were changed.

## Detection and SLO impact

Detection time was **131.2 seconds** from injection to the observed critical
firing state. Webhook delivery took **139.1 seconds** from injection; the runner
confirmed delivery at 141.4 seconds. These are single-exercise observations,
not a statistical mean. Scrape/evaluation cadence, the multiwindow condition,
and the one-minute pending period contribute to detection time.

Both configurations were restored **141.6 seconds** after injection. The client
observed **282 HTTP 503 responses out of 984 requests**, with no transport
failures. One failed request overlaps the start of the runner's recovery phase,
while restoration was still in progress; it occurred before both reloads had
completed. The final ten requests succeeded. All 984 client timings were below
300 ms (maximum 92.0 ms): fast failures violate availability, not this latency SLO.

For this test cohort, availability was **71.34%**. At 99.9%, the allowed budget
was 984 × 0.001 = **0.984 failed requests**. The 282 failures consumed
**286.59 times** that budget. The latency allowance was 9.84 slow requests and
none were observed. These cohort calculations are separate from the rolling SLI.

The post-test Prometheus snapshot showed a 23.19% bad-response ratio in its
available 24h window, versus zero before the exercise. That is **76.81% observed
availability** and 231.87 times the availability budget consumed; latency bad
ratio stayed zero. This window contains earlier traffic and only a short lab
history, with counter estimates between scrapes. It is not a complete production
day or an exact count of this test's requests. Clearing burn alerts means the
recent error rate recovered; it does not restore the spent rolling budget.

## Cause and contributing factors

This was a deliberate configuration fault, not a PHP crash or capacity problem.
Both replicas shared the faulty route behavior, so replica redundancy could not
help. Health/readiness still tested their separate routes successfully; the pods
remained Ready while the main request path failed. No individual is blamed.
The test demonstrates the need for a functional deployment check alongside
probes, and for symptom-based alerts alongside process metrics.

## Recovery

The runner copied back each original generated config, ran `nginx -t`, and
reloaded NGINX. Each pod also had a four-minute independent restore watchdog;
normal cleanup restored service sooner. No image, Helm value, Deployment
specification, or file in Git was changed by the fault. Pod checks sampled during the fault still showed both replicas Ready.
Latency, saturation, and crash-loop alerts did not activate.
